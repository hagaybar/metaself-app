# Adding something to a saved meal just this once — plan

> Branch `add-to-a-saved-meal-just-this-once`. Public issue #10. No numbered decision changes; D41
> (a meal holds a food once, and a search names the food it will not offer) is applied to one more
> search over his foods.

## The problem

The one-day adjust panel on the meals tab of Add something offers Less, As it was, More and Remove.
`RepeatViewModel.addToAdjustment` exists and is tested, but nothing on screen calls it. The screen's
own search box cannot be borrowed for it: `search()` closes whatever is open, which would throw away
the adjustment being built.

Checked against the code before planning — all three latent defects are real:

1. **Identities collide.** An added row takes `id = -(rows.size + 1)`. Meal of two (ids 10, 11): add
   A → -3, add B → -4, remove A → three rows, add C → -4, the same as B. Remove and set-amount both
   match by id, so they then act on two rows.
2. **A later addition lands mid-list on the record.** `position = rows.size`, and the day's rows are
   ordered by position (`SavedMeals.toLoggableItems` sorts by it). Add A (2) and B (3), remove both
   of the meal's own parts, add C → position 2, which sorts it between A and B. A meal whose own
   positions have gaps (the builder appends at `max + 1`) goes wrong without any removal.
3. **A food the meal already holds is refused silently** (`return` when the food id is present).

The existing test asserts only that the added row is in the panel.

## What the panel gains

A **"Put something in"** button under the panel's rows (the builder's wording for the same act,
`builder_add_something`). It opens, inside the panel:

- **Its own search** ("Search your foods", `foods_search`), held on the adjustment, never on the
  screen's search — typing in it closes nothing. Searched with `FoodSearch.matching`, as every search
  over his foods is (D41).
- **The foods it finds**, minus those already in the adjustment. A food left out for that reason is
  **named** — "Cucumber is already in this meal." (`builder_already_in`, the builder's sentence and
  its name-joining), never silently absent. A search that finds nothing at all says "Nothing matches
  “…”." (`foods_no_match`).
- **A way out** of the step that leaves the adjustment as it was: "Not now" (`day_meal_name_cancel`
  wording, a new string so the two can diverge).
- **Picking a food opens the amount step** — the same `HowMuch` block the foods tab uses: grams or
  units, only the ways the food knows on offer and the other with its reason, "Give this a portion"
  where the food has none, the calorie preview, and the too-much refusal (D42). Its buttons read
  **"Put it in"** (`builder_put_it_in`) and **"Not this one"** (`builder_drop_pending`, back to the
  search with the words still typed). The amount starts empty (D4).
- **"Put it in"** appends the row, closes the step, and the panel's total moves. It is a change to
  in-memory state only; the one write — Log it — already runs under the guard (`DayViewModel.logging`,
  `ui/Guarded.kt`). No new action launches a coroutine or touches storage, so there is nothing new for
  the guard to wrap; this is stated rather than a guard added around synchronous code.

The question open in the step follows the food as it is now, as the foods tab's does: a portion given
in the editor reaches it, and a food deleted, hidden or joined away closes it.

## The defect fixes

- `id` = one below the lowest id in the rows (or -1): never reused while a row holds it.
- `position` = one past the highest position in the rows: always last on the record, as in the panel.
- A food already held is never offered (above); `addToAdjustment` keeps its refusal as a backstop.

## Tests (first)

`RepeatViewModelTest` (JUnit 5):
- add two, remove one, add a third → three distinct ids; removing one removes one.
- add two, remove both of the meal's own parts, add a third → logged last, in panel order.
- the whole flow: open the step, search, pick, type an amount, put it in → the row reaches
  `adjusted()` with its calories and `adjusted = true`; the step is closed.
- the panel's search does not close the adjustment (the screen's search still does).
- a food the meal holds is not offered by the panel's search, and is named.
- a portion given in the editor reaches the amount step; a deleted food closes it.

`RepeatScreenRenderTest` (JUnit 4, Robolectric): the panel offers "Put something in"; the open step
draws its search, the already-in sentence and the candidates; the amount step says "Put it in".

## Not in scope

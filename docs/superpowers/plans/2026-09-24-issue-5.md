# A drink is counted by the 100 ml (public issue #5, option 1) — Implementation Plan

**Goal:** a food whose unit is the millilitre (any spelling `Portions.isMillilitres` recognises,
Hebrew included) is entered and shown per 100 ml on its page, never asked what a millilitre weighs,
and logged by a typed amount of millilitres rather than stepped by one.

**Decision:** the owner's, 2026-09-24, recorded on public issue #5 — option 1. Recorded as D56 in
`docs/superpowers/specs/2026-09-24-food-page-design.md`.

**Red lines (stop and report if crossed):** no schema, DAO, migration, backup-format or
provenance-rank change. Nothing converts millilitres to grams (D4). Volume is not a third kind of
fact (decision 2 unchanged): one unit slot, and `ml` is a unit name the app understands.

**Branch:** `a-drink-is-counted-by-the-100-ml`, from `origin/main`. Pushed, no PR.

## The one rule

What is stored does not change: a food counted in ml keeps its per-unit figures **per one ml**, the
shape D53 §3 already writes for a model's per-100 ml worth. Only the form and the words scale:

- **shown** = stored × 100, **saved** = typed ÷ 100, both by decimal point shift
  (`BigDecimal.movePointRight/Left`), never by a float multiply — so 0.64 shows as 64, not
  64.00000000000001, and 3.3 saves as 0.033. The shown value is rounded to 15 significant figures
  first, which removes a double's last-digit noise (0.032999999999999995 → 3.3) and nothing else.
- **A box still showing the stored figure as it opened hands back the stored figure** (the existing
  D54 §8.5 rule, applied at the shown scale), so opening a food and saving it untouched changes no
  stored bit.
- Whether the scale applies is decided by the unit box **as it stands**, live as he types.

One small pure object, `domain/food/PerHundredMillilitres`, holds the test, the two shifts and the
word "100 ml"; every place below asks it.

## What changes

1. **The form** (`FoodForm`): per-unit boxes are at the shown scale for an ml unit (`of`, the figure
   readers, `with`); per-unit ceilings for an ml unit are the per-100 g ones (1000 kcal, 110 g) on
   the typed per-100 ml figure; the refusal says "All four per 100 ml".
2. **The food page and the builder's *Make a food***: the per-unit heading reads *What 100 ml of it
   are worth*; each figure box is said "Calories per 100 ml" (public issue #3's `figureSaid`).
3. **What one weighs** is not drawn on the page for an ml food — unless the stored food already
   holds one: then it stays, with its value and a caption saying a millilitre's weight depends on
   the drink and is not asked, so he can clear it. Nothing is deleted by the app.
4. **Review (D54)**: for an ml food the request sends the per-unit group at the shown scale, with
   `unit_name` "100 ml", and no grams-per-unit (a density; the cross-check has no meaning for it).
   The answer is judged by the per-100 ceilings, rounded to one decimal at that scale (so a suggestion
   of 0.64 kcal is not rounded to 0.6 per ml), shown "Per 100 ml: …", and written into the boxes as
   shown. Save divides as for typing.
5. **Words**: the list row and the page head say "64 kcal per 100 ml"; the retaught notice (D45) the
   same.
6. **Logging an ml food**: the amount ceiling is 5000 (ml), not the count ceiling of 100; the
   amount box has no − / + (Add something's one-day adjuster), and its refusal names ml; the counting
   chip reads "In ml" (the unit as the food spells it). Meal builder waiting/adding rows, Add
   something's picker and the adjuster all go through the same ceiling. Proposal screen: his ml
   food's worth line says "per 100 ml" with the figures for 100 ml, not "per ml" rounded to whole.
7. **Barcode scan's add-a-food form**: not changed. A scanned packet is cached as per-100 g figures
   (`Product`, a table); marking it ml would need a column. Reported, not built.
8. **D56** recorded in the food-page spec, with an invented worked example.
9. Version 0.49.0 (versionCode +1).

## Tests (written first, failing before)

- `PerHundredMillilitresTest` (JUnit 5): recognises spellings; shifts are exact; noise removed.
- `FoodFormTest` (JUnit 5): an ml food opens per 100 ml; typed per 100 ml saves per ml; untouched
  round trip returns the identical stored figures, including one with float noise; per-100 ceilings
  and wording; a review suggestion written as shown; a non-ml food unchanged.
- `ReviewPromptTest` / `ReviewResponseTest`: request for an ml food sends "100 ml", figures × 100,
  no weight; the answer is judged by per-100 ceilings.
- `FoodWordingTest`, `RetaughtWordingTest`: "per 100 ml".
- `BelievableAmount` / repeat / builder state: 250 ml is believable, 6000 ml is too much.
- `ItemToLog` (proposal): his ml food's rate line is per 100 ml.
- Render (JUnit 4 / Robolectric): food page heading and said names per 100 ml, no weight box for an
  ml food, weight box kept with its value for one that has a stored weight; adjuster's ml row has no
  − / +; chip reads "In ml".

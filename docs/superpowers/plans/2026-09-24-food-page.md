# Every food has its own page (D55) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended)
> or superpowers:executing-plans to implement this plan task-by-task. **One task per agent.** Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** every food in *My foods* opens a full-screen page of its own — name, summary, the review
(0.46.4, unchanged), the three groups, Save / Leave it alone, *Where it's used*, and Join / Hide /
Delete — instead of the editor drawn inside the list. The list keeps search, filters, choosing, and
the join pick and question.

**Spec:** `docs/superpowers/specs/2026-09-24-food-page-design.md` — **D55**. Read all of it before
starting any task. §5 (joining from a page), §6 (hide/delete from a page), §7 (the food gone) and §8
(process death) are the parts most easily built wrong. Its three *Questions for the owner* have
defaults; build the defaults unless the owner has answered.

**Branch:** `every-food-has-its-own-page`. Do not push until the hand-over task.

**Architecture:** A new destination `food/{foodId}` with its own `FoodPageViewModel`, which takes
over from `FoodsViewModel` everything about ONE food: the form, Save, the review, hide/unhide, the
delete question. `FoodsViewModel` keeps everything about the list. The page tells the nav host it is
finished through one `closing` value in its state (saved, hidden, deleted, join, gone); the nav host
pops once, and hands the list a result through the list entry's `SavedStateHandle` (`joinFrom`,
`hidden`). *Where it's used* is one new observed read (`FoodRepository.observeUse`).

**Order, and why:** the page is built **beside** the inline editor (Tasks 3–4) and only then does
the list stop using the editor (Task 5), so every commit builds, passes, and is installable. Moving,
not copying, is finished in Task 5, which deletes the editor and its tests from the list.

**Tech Stack:** Kotlin 1.9.22, JVM 17, Compose BOM 2024.02.00, Navigation Compose, Hilt. JUnit 5 +
Truth for everything pure and for view models; JUnit 4 + Robolectric only for render and session
tests (`CLAUDE.md`: never mix the two `@Test` imports in one file). No new dependency.

**Schema: NONE.** No entity, no database version, no `app/schemas/…/6.json`, no migration, no backup
format change. **One new read-only DAO statement** (Task 1) and one existing statement made
observable. If any task finds itself editing `FoodEntities.kt`, `MetaSelfDatabase` or `app/schemas`,
stop: the plan is wrong, not the code.

**Room tests are CI-only.** Task 1's `RoomFoodRepositoryTest` cases skip locally on this aarch64 box
(`assumeSqliteRuntime()`). The SQL is checked locally by a new `tools/check-food-use.py` against
Python's `sqlite3` built from the committed version-5 schema, modelling the app's read path. That
proves the statements parse and count what the spec says; it does not prove Room's `Flow`
invalidation, which only CI's Room test does. Do not report the Room tests as passing before CI runs.

**Before every Gradle command:** `export ANDROID_HOME=/home/ubuntu/android-sdk`; use
`~/bin/gradlew-safe`, never bare `./gradlew`; redirect output to a file and check `$?`, never pipe a
build whose result you report; stage by explicit path, never `git add -A`. Locally, exactly the eight
Room classes listed in `CLAUDE.md` skip — nothing else may.

**Public repository.** Every comment, KDoc, test name and string is published. Invented figures only;
the foods, brands and meal names below are the spec's inventions. Never state a frequency or a real
count. A test name prints in CI — read it as prose.

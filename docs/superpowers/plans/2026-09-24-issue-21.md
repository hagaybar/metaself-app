# Tapping a saved meal opens it (public issue #21) — Implementation Plan

**Goal:** on *Add something* → *My meals*, tapping a saved meal's row opens its one-day view (the
adjuster: parts, amounts, *Log it* / *Leave it alone*) and writes nothing. Logging is the press on
*Log it*. The separate *Adjust* button goes; *Change it* stays and opens the meal builder. On both
screens that list saved meals, a tap on a row now opens it and never writes to the day.

**Decision:** the owner's, 2026-09-24, recorded on public issue #21.

**Branch:** `tapping-a-saved-meal-opens-it`. Not pushed.

## What changes

1. `RepeatScreen.BuiltMeal`: the row's click opens the adjuster (`onBeginAdjusting(index)`), with
   `Role.Button` and an `onClickLabel` naming the meal ("Open <meal> for today"). The *Adjust*
   `TextButton` is removed. *Change it* keeps opening the builder and is said with the meal's name
   (`said_for`), so each copy is its own control (public issue #3).
2. `RepeatScreen`'s `onRepeat` parameter goes, with its wiring in `MetaSelfNavHost` and the
   simulation shell (`sim/SimulatedApp.kt`): nothing on the screen logs a meal in one tap any more.
3. **An unchanged *Log it* must log exactly what the old tap logged.** The old tap wrote
   `LoggedMeal(SavedMeals.toLoggableItems(meal), meal.id, adjusted = false)`. `adjusted()` builds its
   items with the same function over `asDefined.copy(components = rows)` and `adjusted` from
   `SavedMeals.wasAdjusted(asDefined, rows)`; with the rows untouched both are the same. Pinned by a
   view-model test comparing the two values for equality.
4. **An empty meal** still opens on a tap (so *Put something in* is reachable), says it has nothing in
   it yet, and its *Log it* is disabled — as is *Log it* for a meal none of whose parts can be costed.
   New `Adjusting.canLog`: nothing blocked, and at least one loggable item.
5. The note above both tabs (`repeat_note`, D37) no longer says a tap puts a meal on the day.
6. Unused `repeat_adjust` string removed. KDoc updated where it says the row logs.
7. Specs: dated amendment notes, original text kept — milestone-1 design step 9, step 13 ("One tap
   still logs a meal exactly as it was") and D37 (which quotes the note). The foods-and-meals
   manager spec says only that logging stays on *Add something*, which remains true: no note.

## Tests (written first, failing before the change)

- Render (`RepeatScreenRenderTest`, JUnit 4 / Robolectric):
  - tapping a meal's row asks to open that meal and logs nothing (the screen no longer takes a log
    callback; the row's click calls `onBeginAdjusting(index)`);
  - no *Adjust* button is drawn;
  - *Change it* still opens the builder for that meal, and is said with its meal's name;
  - the row is a button, and its click label names the meal;
  - in the adjuster, *Log it* calls `onLogAdjusted`, *Leave it alone* calls `onCancelAdjusting`;
  - an empty meal opened: says it is empty, *Log it* disabled.
- View model (`RepeatViewModelTest`, JUnit 5):
  - opening a meal and logging it unchanged equals the old direct log;
  - an empty meal opened cannot be logged (`canLog` false, `adjusted()` null).
- Existing expectations that change: `a meal he built can be opened for one day only` (looked for
  the word *Adjust*), and the note test (`REPEAT_NOTE`).
